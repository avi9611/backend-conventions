# Migrations

> Read this before you change the schema.
>
> **Status in this project:** in force from day 1
> **Last verified against the code:** 21 August 2026

---

## 1. What & why

Autogenerated migrations are powerful and, in any real schema, subtly wrong in a handful of
specific ways that each cost a session before they are understood.

A model the generator cannot see. An enum type it will not drop. Foreign-key cycles it orders
wrongly. Every one produces a migration that looks fine and fails on apply, or worse, applies and
quietly drops something.

This file is the list of traps, because "run autogenerate" is not safe without them.

Most of §3 is Alembic and Postgres. The shape of each trap exists in every migration tool.

---

## 2. The rules

- **Register every new model in the one import file**, or the generator cannot see it and will
  emit either nothing or a drop.
- **Read every generated migration before you apply it.** Autogenerate is a first draft.
- **Every new database enum type needs an explicit drop in the downgrade.**
- **Upgrade and downgrade must both apply cleanly.** Test the round trip, every time.
- **Migrations run as a deliberate step**, never automatically on container start.
- **Never edit a migration that has been applied anywhere but your machine.** Write a new one.
- **A migration that moves data is a different thing from one that changes shape.** Say which it
  is in the message, and make the data step restartable.

## 3. The traps

### 3a. The invisible model

**Symptom.** The generated migration is empty. Or worse, it contains a drop for a table you did
not touch.

**Why.** Autogenerate compares the model metadata against the database, and a model is only in
that metadata if something imported it. One file of side-effect imports makes that happen.

**The catch.** Every one of those imports looks unused to every linter and every autofixer. One
"remove unused imports" pass and the generator goes blind.

**The fix.** Exclude that file from autofixers, explicitly, in the linter config, and put a
comment at the top saying why.

### 3b. The enum type that will not drop

**Symptom.** After a downgrade and re-upgrade: "type already exists".

**Why.** Creating an enum makes a database type. Dropping the table or the column does **not**
drop the type. So after a downgrade the type is orphaned, and the next upgrade fails.

**The fix.** Every migration that creates an enum type drops it explicitly in the downgrade.

### 3c. The same enum created twice in one migration

**Symptom.** "Type already exists", inside a single upgrade. And because the whole upgrade runs in
one transaction, everything rolls back, so it reads as a broken migration rather than as one
duplicated statement.

**Why.** You pre-created the type, then passed the *same* enum object to the create-table call,
which emits a second create with no existence check.

**The fix.** Declare it with creation switched off, and create and drop it explicitly.

### 3d. Foreign-key cycles

**Symptom.** A from-scratch migration fails with "relation does not exist". The same schema
migrates fine incrementally.

**Why.** The table sort is not cycle-aware. Two tables that reference each other cannot both be
created first.

**The fix, and it is cheap.** Mark one side of the cycle as "alter afterwards", which tells the
tool to emit that constraint as a separate statement once both tables exist. Then everything
orders correctly with no manual work.

**Do this on every cycle you create.** One schema I know has three. The newest carries the flag
and regenerates cleanly. The two older ones do not, and a full regeneration of that schema needs
manual reordering. That is a permanent property of the schema now, not a bug, and it is written
down so a regeneration does not rediscover it the hard way.

### 3e. The squash

At some point the migration folder gets long enough that a fresh setup takes minutes and nobody
reads the history. Squashing to a single initial migration plus the seeds is reasonable.

Two things to get right:

- **Keep the originals** in a clearly named backup folder. Someone will need to know what
  happened.
- **Be clear which seeds run in a migration and which run in an application seed script.** They
  are different paths with different triggers, and conflating them is how starter data goes
  missing on one environment.

### 3f. Running migrations against the wrong database

**Symptom.** The migration reports success and the application still sees the old schema.

**Why.** Run from your machine, the host name in the environment file resolves to a different
database than the one the application container sees.

**The fix.** Run migrations inside the container, or make the two names impossible to confuse.
And write it in `CLAUDE.md`, because it costs half an hour every single time.

## 4. Decisions this project must make

| Decision | Options | What we chose | Why |
|---|---|---|---|
| File naming | date-prefixed, or revision hash only | | |
| Enums | database enum types, or strings with a check constraint | | |
| Are downgrades supported? | yes and tested, or forward-only | | |
| Where migrations run | a deploy step, an init container, or on app start | | |
| Data migrations | in the same file, or a separate script | | |
| Zero-downtime | required, or a maintenance window is acceptable | | |

Row 1: date-prefixed sorts readably in a folder listing. Worth it.

Row 3: "forward only" is an honest position and many teams take it. What you must not do is claim
downgrades work without testing them, because then you discover in an incident that they do not.

Row 4: **never on application start.** Two containers starting at once both run it. And a
migration that fails takes your application down with it, rather than failing a deploy step you
can look at.

Row 6: if yes, then every schema change becomes two or three deploys. Add a column nullable,
backfill, then make it non-nullable. Rename becomes add, dual-write, backfill, switch, drop.
Decide before the first breaking change, not during one.

---

## 4a. The zero-downtime patterns, if you need them

| Change | The safe sequence |
|---|---|
| Add a column | nullable, or with a default. One deploy |
| Add a non-nullable column | add nullable, backfill, set non-nullable. Three steps |
| Rename a column | add the new one, write to both, backfill, read from the new one, drop the old. Four deploys |
| Drop a column | stop reading it, deploy, then drop. Two deploys |
| Add an index | build it concurrently, outside a transaction |
| Change a type | usually a new column plus a backfill |

Note the index row. Building an index normally takes a lock that blocks writes on a large table
for as long as it takes. Concurrent index builds cannot run inside a transaction, which most
migration tools wrap around your migration by default. That is a real thing to configure, not a
detail.

## 6. New-migration checklist

1. **Register the model** in the import file first.
2. Generate the migration, inside the container.
3. **Read it.** Did it see your model? Did it try to drop something it should not have, because
   it could not see one?
4. **For every new enum type**, add the drop to the downgrade.
5. Apply up, then down, then up again.
6. If you introduced a foreign-key cycle, mark one side "alter afterwards".
7. If it moves data, make it restartable and say so in the message.

## 7. How to re-check this doc

> Paths below are examples from one tree. Adjust them to yours. What matters is the check,
> not the path. Where a count is given, it is the count **for this project**, so fill it in
> the first time you run it.

```bash
# Migration count.
ls migrations/versions/*.py | wc -l
```

```bash
# Side-effect imports that keep models visible. A new module's models must be here.
grep -cE "^\s*from app\." app/core/alembic_models_import.py
```

```bash
# Every enum-creating migration must carry a drop in its downgrade.
for f in $(grep -rln "sa.Enum\|SQLEnum\|postgresql.ENUM" migrations/versions/); do
  grep -q "DROP TYPE" "$f" || echo "NO DROP TYPE: $f"
done
```

```bash
# Round-trip the head migration.
alembic upgrade head && alembic downgrade -1 && alembic upgrade head
```
